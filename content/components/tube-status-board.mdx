## Get line status

```ts
import TflClient, { sortLinesBySeverityAndOrder } from "tfl-ts"

const tfl = new TflClient({
  appKey: process.env.TFL_APP_KEY!,
})

const data = sortLinesBySeverityAndOrder(
  await tfl.line.getStatus({
    modes: ["tube", "elizabeth-line", "dlr", "tram", "overground"],
  }),
)
```

`data` is the public `tfl.line.getStatus()` row type, aliased here as `StatusLine`. Sort before you pass it in. The board does not fetch.

On this docs site, `getCachedLineStatuses` in `@/lib/tfl/status-data` wraps the same call with Cache Components.

## Render

```tsx
import { TubeStatusBoard } from "@/components/tfl/status/tube-status-board"

export default function Page({ data }) {
  return <TubeStatusBoard data={data} />
}
```

Good Service titles auto-abbreviate at narrow grid widths (full → middle → 3-letter code) via [`Line title`](/docs/line-title). Tier data lives in `lib/tfl/line-names.ts`.

## Variations

### Underground and Elizabeth only

```tsx
import {
  DEFAULT_STATUS_LINE_IDS,
  TubeStatusBoard,
} from "@/components/tfl/status/tube-status-board"
import { getCachedLineStatuses } from "@/lib/tfl/status-data"

export default async function Page() {
  const data = await getCachedLineStatuses(DEFAULT_STATUS_LINE_IDS)
  return <TubeStatusBoard data={data} />
}
```

## Announcements

TfL returns an array of `lineStatuses` per line. A single story can appear two or three times with different severity codes, because the code names the *kind* of status (Suspended, Special Service, Planned Closure), not the incident. The board shows what a passenger expects: what is happening now, once.

By default it:

1. Keeps rows TfL marks as valid now (`validityPeriods[].isNow`). Rows with no validity window are live and always kept. Future planned work is the Week ahead Block's job — a line whose only announcement is future reads as Good Service.
2. Collapses equal paragraphs, or one paragraph that fully contains another, into the longer text painted at the worse severity.
3. Strips mode / line prefixes that repeat the card title (`LONDON TRAMS:`, `BAKERLOO LINE:`).

Each disruption shows a gray platform-style severity chip (`Severe Delays`, `Part Closure`, …) inline at the start of TfL's paragraph.

Each step is opt-out:

```tsx
{/* Keep future windows too */}
<TubeStatusBoard data={data} currentOnly={false} />

{/* Show every TfL paragraph even when one contains another */}
<TubeStatusBoard data={data} dedupe={false} />

{/* Keep LONDON TRAMS: prefixes */}
<TubeStatusBoard data={data} rawReason />

{/* TfL's array verbatim */}
<TubeStatusBoard data={data} currentOnly={false} dedupe={false} rawReason />
```

## Props

| Prop | Type | Description |
|------|------|-------------|
| `data` | `readonly StatusLine[]` | Rows from `tfl.line.getStatus()`. Missing or `undefined` renders empty. |
| `hideHeader` | `boolean` | Omit the board header. |
| `compact` | `boolean` | One column — for a narrow side slot. |
| `currentOnly` | `boolean` | Keep only TfL `isNow` announcements (default `true`). |
| `dedupe` | `boolean` | Collapse equal or contained paragraphs (default `true`). |
| `rawReason` | `boolean` | Keep TfL's unstripped `reason` string (default `false`). |
| `children` | `ReactNode` | Optional slot below the status list. |

Official colours come from `tfl-ts` CSS helpers inside the board. Fixtures can show severe delays without waiting for a live incident.
