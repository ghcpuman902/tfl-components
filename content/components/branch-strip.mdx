## Purpose

Atomic branched schematic strip — lane×pos nodes and edges with an explicit `lineColor`. Use when you already have a prepared render model.

## Installation

Ships with the [line-strip](/interfaces/line-strip) registry item:


### When to use which

| Need | Use |
|------|-----|
| TfL colour, label recipes, prepared schematic | `LineStrip` with `schematic={…}` |
| Full control over a prepared lane×pos model | `BranchStrip` |

`BranchStrip` is a **rendering primitive**. Prefer `LineStrip` for data-driven callers; drop to this atom when you already have a render model.

## Composition

`BranchStrip` takes a `LineSchematic` (lane × pos nodes and edges), an explicit `lineColor`, and optional prepared `nodeLabelLines` / `segmentStates`. It does not fetch TfL data or look up label recipes.

`LineStrip` is the **molecular** wrapper that applies recipes and colour, then renders `BranchStrip`.

### Geometry

Author separate horizontal and vertical schematics — do not rotate one graph. Shared stations that diverge and converge (Camden Town, Kennington) are single nodes; parallel corridors that share a name (Euston) use duplicate nodes with a shared `stationKey`.

Lane joins follow the **Line Diagram Standard** (not the geographic Tube map): circular arcs at 45° / 90°, never freeform Beziers. Horizontal strips use in-carriage §6 joins (45° S when space allows, otherwise 90° R). Vertical strips use platform §11 branch curves (90° with R3n / R4n).
